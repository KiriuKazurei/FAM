# 撤销坐上拍子：移动的回退也是任务（增量 25）

## 1. 描述问题

21 号账的残留第 2 条："大文件的撤销逆操作仍同步（撤销跨卷移回 = 一次大复制在 GUI 线程）"
——20 做的撤销，其移动分支走的还是 `fam_path_op` 的同步旧路：撤销一个刚花了五分钟跨卷
搬来的大文件，Ctrl+Z 再冻五分钟。21 把传输变成任务之后，这是全壳**最后一个同步大操作**。

## 2. 分析问题

撤销的两个分支本来就不对称：复制撤销是**一次 unlink**（没有中间、无可等待），移动撤销
是**一次传输**（跨卷时有全部的中间）。所以只动移动分支：

- 弹出的条目**塞进待定任务**（`PendingTransfer.undo = true`，条目随行）——完成即撤销的
  句子；失败或取消则**条目回栈**，"被挡住"与"被忘记"仍是两个事实，回栈即仍可重试；
- 完成分支**绝不推新条目**——否则 Ctrl+Z 会撤销撤销，重做语义从后门漏进来；
- 复制撤销保持同步（20 的原话照旧：一次 unlink 没有中间）。

## 3. 解决方式

`MainWindow::undoLastTransfer` 的移动分支改 `transferBegin(to, from)` 并把弹出的条目
随行入待定队列；`pollTransfers` 的完成/取消/失败分支按 `undo` 标志分岔（完成=句子、
失败/取消=回栈）。self-check 的撤销步在第二次 Ctrl+Z 后等待队列清空——磁盘断言说的是
结算后的世界。

## 4. 效果评估

**证据**（light/dark 两遍一致）：`undo job: moved ... back to ...`（移动回退作为任务在
拍子上完成）+ `copy-undone=1 move-undone=1`（磁盘断言照旧全过）。cargo 38 个二进制
全绿；clippy/fmt 干净；abi-smoke 连跑两遍 ok；model-smoke ok。

**代价**：撤销的完成推迟到下一拍（≤250ms，人不可感）；无新增代码面（复用 21 的全套
任务机器）。

**残留**：撤销的取消（Esc）会把条目回栈——重试语义对，但"取消我的撤销"这个表述留给
下一次碰到时再想；无重做（20 的原判不变）。
