# 对账采样贵在一次路径打开，而不是贵在一个 stat

- 增量：4（`fam-sched` 目录对账 `WatchSet::sweep`）
- 提交：本次提交（前序：`683f1fd` 懒目录缓存、`a246189` 增量 3 留档）
- 涉及：`crates/fam-sched/src/reconcile.rs`、`crates/fam-sched/src/pipeline.rs`

## 1. 描述问题

增量 4 的兜底机制是"给每个在看的目录周期性取一次 last-write time"（为什么需要它见
[notify-watch-loss-is-invisible.md](notify-watch-loss-is-invisible.md)）。计划里这条被当作
**廉价探针**写下来：一次 `stat` 几微秒，一次目录重读几百微秒，所以"探一下，必要时才重读"
比"定期全量重读"便宜两个数量级。

沿用的预算是 `SWEEP_BUDGET = 64` 个目录 / 2 秒一拍。要验收它，需要先知道一次采样到底多少钱。
实测结果推翻了这个前提：**本机一次取目录写时间是 187–223µs**，而一次完整的 188 条目录重读是
231µs（`fam-bench check` 本次 `read_flat_win32` floor）——探针只比重读便宜 1.2 倍，不是两个数量级。
按 64/拍算，消费者线程每 2 秒要被占去 12.3ms（0.6%），而且这个数会随机器状态漂移。

## 2. 分析问题

一次性探针（临时 example，release，200 个临时目录，每种取多轮 floor）。**三个 API、三种工作集：**

| 取写时间的方式 | 200 个不同临时目录 | 混合工作集（含 `C:\Windows` 等长路径） | 同一个目录取 200 次 |
| --- | --- | --- | --- |
| `fs::metadata(dir).modified()` | 206.5 µs | 209.3 µs | 201.6 µs |
| `FindFirstFileExW("dir\\.")` + `FindClose` | 222.5 µs | 223.0 µs | 219.9 µs |
| `GetFileAttributesExW` | 187.6 µs | 193.7 µs | 193.5 µs |

另一次运行（同一台机器、同一份代码）是 199.8 / 214.5 / 186.9，即变体间差异（≤15%）与运行间
摆动同量级。**换 API 省不下钱。**

**四个对照，把贵在哪钉住：**

| 对照 | 单次 |
| --- | --- |
| 用户态空循环（harness 下界） | 0.030 µs |
| `GetCurrentDirectoryW`（进内核但不建文件对象） | 0.4 µs |
| `metadata()` 打一个**不存在**的路径（解析失败即返回） | **140.5 µs** |
| `metadata()` 打存在的目录 / 文件 | 207.6 / 211.6 µs |

三条结论：

1. **不是缓存冷。** 同一个目录取 200 次和 200 个不同目录各取一次，价钱一样。
2. **不是目录特有。** 文件的 211.6µs 与目录的 207.6µs 在噪声内。
3. **贵在建文件对象这一步，且在数据到手之前。** 一个必然失败的路径解析已经要 140µs，
   占成功情形的七成。也就是说这钱花在"把这个名字解析到一个对象"上，谁调都一样。
   `GetCurrentDirectoryW` 的 0.4µs 说明这不是"syscall 本身贵"。

**一个必须点破的假对照**：直接给 `GetFileAttributesExW` 传 `NULL` 得到 0.1µs/次。这**不是**
syscall 下界——参数检查在 `kernelbase` 里就把调用挡回去了，根本没进对象管理器。把它当作
"syscall 只要 0.1µs"会导出完全错误的预算。

**税源未证实。** 这个量级（一次元数据查询 0.2ms）明显高于常见值，指向文件系统筛选栈
（实时防护的 minifilter、存储/备份类驱动）。本次没有枚举驱动、没有做关闭对照（那要动别人的
机器状态），所以只记录" magnitude 实测、归因未验证"。

**探针到底比"直接重读"省不省。** 用已有 case 折算（公式随表给出，条目单价取本次
`fam-bench check` 的 `min_us ÷ entries`，不是另一次会话）：
`read_flat_win32` 是 231µs/188 条 = 1.228µs/条，而探针是 190µs 固定一笔 →
**交叉点约 155 条**：小于它，探针比重读还贵；目录越大探针才越划算。
对照另一头：缓存命中后取一屏是 12µs（本次 `viewport_from_cache` floor，20 次查找 + 全部 60 行
视口），一次探针是它的 **16 倍**——所以"每次读取顺手验一下"这条路直接排除，验证不能挂在读路径上。

## 3. 解决方式

既然单价不可控，就把**预算从"多少个"改成"多少时间"**：每拍允许花 `SWEEP_WINDOW = 4ms`，
能装几个算几个，单价由上一拍实测得来。

```rust
// pipeline.rs:404-409
next_sweep = now + RECONCILE_INTERVAL;
let budget = pacer.budget(consumer_watches.len());
let started = Instant::now();
let report = consumer_watches.sweep(budget, write_time);
pacer.observe(report.samples, started.elapsed());
```

`reconcile.rs:207-241` 的 `SweepPacer`：`budget = window / ns_per_sample`（夹在
`[watched>0 ? 1 : 0, watched]`），`observe` 以 1/4 权重折入新单价。三个细节各自有理由：

- **种子用实测值** `SEEDED_NS_PER_SAMPLE = 200_000`，第一拍就不会乐观过头。
- **下界 1 个**（只要有监视）：单价估高时若降到 0，就再也测不到真实单价，估计永远回不来。
- **`sweep` 返回 `SweepReport{signals, samples}`**：监视可能在算完预算与真正扫描之间被摘掉，
  按请求数记账会把单价算便宜。`samples` 是真正取样数。

**仍然用 `std::fs::metadata`。** §2 已证明三个 API 等价，于是"为此给 `fam-sched` 加
`windows-sys` 依赖"没有换来任何东西——不加。这条是省下的一次依赖面扩张，理由写在码里。

`RECONCILE_INTERVAL` 保持 2s：它现在只决定"最坏多久轮到一次"，不再决定占用率。

## 4. 解决方式效果评估

**正面证据。** 单元测试
`a_budget_is_priced_from_measured_cost_not_a_fixed_count`：种子 200µs 时 4ms 买 20 个；
连续 20 拍改成 2µs/个之后，同一窗口能覆盖整个 1000 项集合（`budget(1000) == 1000`），
30000 项时给 1522（≈4ms/2.6µs，EWMA 尚未收敛，断言写成区间 1000..4000 以免钉住收敛速度）；
单价高过窗口时下界为 1。占用率上界由构造给出且与机器无关：
`SWEEP_WINDOW / RECONCILE_INTERVAL = 4ms / 2s = 0.2%`。

**换算（公式：整圈时长 = N / (4ms ÷ 190µs) × 2s，本机每拍约 21 个）：**

| 在看的目录数 | 本机整圈 | 若某台机器单价 2µs（每拍 2000 个） |
| --- | --- | --- |
| 21（一拍即满） | 2 s | 2 s |
| 100 | ~10 s | 2 s |
| 1000 | ~95 s | 2 s |
| 20000 | ~32 min | 20 s |

**代价。**

- `reconcile.rs` 多一个 24 行的 `SweepPacer` 与一份 `SweepReport`；"预算"从常量变成运行时量，
  读代码的人不再能一眼说出"每拍几个目录"。
- 本机整圈时长被单价定死，慢机器上兜底就是慢——这是如实的取舍，不是可以调掉的参数。
- 测试时长：`cargo test -p fam-sched` 单测 34 条 0.01s，集成 13 条 8.2s（对账相关三条要等真实
  采样拍）。
- 扫描期间持有 `WatchSet` 互斥锁最长一个窗口（4ms），`mark_seen` 与 `watch/unwatch` 会被它挡住；
  **这个阻塞时延未实测**。

**残留风险与局限（没解决什么）。**

1. **贵这件事本身没解决**：仍然每目录一次路径打开。税源（minifilter 还是驱动栈）没有验证，
   所以"换一台机器会不会便宜 100 倍"只是猜测。要真验证得在同机装上/卸下筛选驱动做对照，
   这次不动机器状态。
2. **探针与重读的交叉点（约 157 条）是折算**，用 `read_flat_win32` 的 1.21µs/条目外推，
   没有按目录规模分档实测。若增量 5 之后"大目录"成为主要场景，这条要重测。
3. **加一个监视要 904µs**（200 个目录、release、floor；最差 1475µs），其中 notify 的
   `add_watch` 白付两次 `path.is_dir()`（`windows.rs:169`、`:177`）。本增量没有绕开它，
   因为绕开就等于自己实现 `add_watch`。增量 5 若要"每开一个目录加一个监视"，
   这笔钱是读目录（231µs/188 条）的 3.9 倍，必须先决定值不值。
4. 时间预算只约束**扫描本身**，不含 `batcher.absorb()` 与后续 flush；一拍产出的重扫条数没有上限
   （极端情形：整圈目录同时消失）。未处理，因为触发条件是"父目录被整体删除"，那种时候正确行为
   本来就是全部重扫。
