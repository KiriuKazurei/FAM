# 窗口管得起的撤销（增量 20）

## 1. 描述问题

增量 14 的残留清单里挂着两个"中"，撤销是其中之一：

> 一次拖放直接改盘，Ctrl 拖会留下第二份。撤销要么靠日志回放、要么靠事务，两者都比
> "这次要能搬文件"大一个数量级。严重度：中（误拖一个文件夹进另一个文件夹，人现在只能
> 自己拖回来）。归属：撤销/回收这一层。

一年来的状态：拖错的人只能凭记忆自己拖回来；Ctrl 拖出的第二份要么手删、要么留着。
agent 那一面自始就有 `fs_delete`，但删除的规则（非空目录拒绝、符号链接只删链接本身、
读不出的条目不算空）写在 MCP 的 `mutations.rs` 里——shell 的撤销要用它，就得起第三份
拷贝。

## 2. 分析问题

### 日志回放与事务都太大，但两者之间还有第三条路

14 的账把撤销框在"日志回放或事务"里，那条判断对**任意**操作成立，对**本窗口自己刚做的
传输**不成立：一次 drop 的全部逆信息就在返回值里——`Transferred{from, to, action, by}`。
移动的逆是移回去（原位置按定义空着，除非被占——"永不覆盖"会替人说话）；复制的逆是删掉
这份重复（删的正是本窗口刚创建的那个路径，别的什么都不碰）。不需要回放，不需要事务，
只需要把返回值记住。

范围的取舍随之定下：**只记本会话本窗口的传输**（一个栈），一次 Ctrl+Z 弹一层。栈深是
"这台窗口做过的传输数"，每个条目都可独立失败：逆操作被"永不覆盖"挡住时**条目留在栈上**，
"被挡住"与"被忘记"是两个事实，只有第二个丢数据。agent 面不加工具——`fs_move` 本来就在，
agent 想撤销就是再发一次 move；撤销的逆信息本来就在审计里。

### 删除原语住进 fam-svc-fs：第三份拷贝是拒绝的理由

撤销复制需要一个删除。MCP 的 `fs_delete` 从 12 起自带全套守卫，shell 再写一遍就是三份
"非空目录拒绝"的措辞迟早漂移。`remove_path` 收进 fam-svc-fs——错误变体的句子逐字从
MCP 搬来（`still has entries in it` 这句被门测试钉着），MCP 的 `fs_delete` 改为委托，
本层只留门与 JSON 形状。

### 一次被自己骗了的调试

smoke 的第二轮删除断言一开始红着，排查走了弯路：加打印、怀疑 DLL 陈旧、怀疑 Windows
延迟删除——最后发现 `secondRefused` 这个变量名存的是 `pathDelete` 的返回值，而那个返回
值的语义是"删除成功"：第二次调用被拒（返回 false）时变量恰好为 false，被我从断言里
当成了"没被拒"。**行为从头就是对的，错的是断言的命名。**名字改成 `secondSucceeded`、
断言改成 `!secondSucceeded && 句子含 "cannot open"` 之后一次绿。留档的原因：变量名与
返回值语义相反时，绿灯与红灯都不可信——这一条与 16 的"只有截图暴露"是同一族。

## 3. 解决方式

- `crates/fam-svc-fs/src/lib.rs`：`remove_path(path) -> Removed{path, kind}`——文件删除、
  空目录删除、非空目录按名拒绝、符号链接只删链接本身、读不出的条目不算空；四个错误变体
  （`CantOpen`/`DirectoryNotEmpty`/`CantCheckEmpty`/`CantRemove`）的句子与 MCP 原实现
  逐字一致；两条单元测试（二连删、非空拒绝+空目录走）。
- `crates/fam-svc-mcp/src/mutations.rs`：`fs_delete` 改为委托 `remove_path`，本层只剩
  门与 JSON；门测试（钉住句子的那条）原样绿。
- `crates/fam-ffi/src/lib.rs`：`fam_path_delete`（导出 29→30，审计 `path.delete`，
  Ask 族）；ffi 过线测试：文件删掉、二连删"cannot open"、非空目录拒绝且目录还在。
- `apps/fam-shell`：`FamBridge::pathDelete`；`MainWindow` 的 `m_undoable` 栈
  （`handleDrop` 按核心回答的 `from`/`to`/`copy` 入栈，只记真的发生了的传输——落回原
  列的那次不入栈，本来就没有东西可逆）、`Ctrl+Z`（`QKeySequence::Undo`）→
  `undoLastTransfer()`：移动用 `pathOp(to, from)` 移回，复制用 `pathDelete(to)` 删副本；
  失败回栈重试，成功清栈并报终态。
- self-check：`undoForSelfCheck`——两发**真的 Ctrl+Z**（`sendEvent` 到窗口，走
  `keyPressEvent` 的同一条路），断言全在磁盘上：第一键之后源在、副本不在；第二键之后
  副本位置有了、原位置没了。时间线尾部让位（清理步 10100→10500，抓帧 10600→11000）。
- `abi-smoke`：`delete=1` 进导出闸门行——文件删、二连删拒、非空目录按名拒且目录还在。

## 4. 解决方式效果评估

### 正面证据

**无头那一步的原文**（fresh 树，light 与 dark 两遍逐字一致）：

```
self-check undo: copy-undone=1 (origin=1 copy=0) move-undone=1 (origin=0 dest=1)
```

`copy-undone` 的两个断言合起来才是证据：副本位置没了**并且**源位置还在——只看副本消失
不算数，删除了源的反向移动也会长这个样子。`move-undone` 同理反向。

**核心侧**：`cargo test --workspace` 38 个二进制全绿（fam-svc-fs 两条、ffi 一条新增）；
clippy `-D warnings` 干净；fmt 干净。MCP 的门测试（含钉住句子的那条）原样绿。

**壳侧**：light/dark 两遍退出 0，对比度 17 对全过，17c–19 的全部断言原样绿；
`abi-smoke` 连跑两遍 `-> ok`（新 `delete=1`）；`model-smoke` ok。

### 两处自记

1. **`secondRefused` 的命名事故**（见第 2 节）。修法是把变量名改成它真正的语义
   （`secondSucceeded`），断言改成对失败路径的句子断言——名字与语义对齐之后，红绿才有
   含义。
2. **`handleDrop` 只在 `done > 0` 时有东西可记**，而"落回自己的列"那一步被既有的守卫
   拦在调用之前——所以栈里不会有"零传输"的条目，撤销永远不会花在无事发生的那一拍上。
   这是既有守卫送的，不是这次写的，记下它的归属。

### 代价

- 每次拖放入栈一个三元组（三个 QString 的内存，随会话增长——一次会话的拖放数以十计，
  无单独计时）。
- fam-svc-fs 约 60 行 + MCP 净减 25 行（守卫搬走）+ ffi 约 40 行 + 壳约 80 行。
- 撤销的移动本身是一次 `pathOp`（审计 `path.move` 一条），撤销的复制是一次
  `path.delete`（审计一条）——撤销不免费也不隐身，跟拖放本身同样记账。

### 残留风险与局限（这次没解决什么、为什么）

1. **栈只在内存里**：关窗即忘，跨会话的撤销不存在——那是 14 说的日志回放层，仍然不做。
   严重度：低（一次误拖到发现，间隔是秒级）。
2. **没有重做**（Ctrl+Shift+Z）。撤销之后再拖一次是同一条路，重做栈服务的场景（撤销后
   反悔）比撤销本身少一个量级。严重度：低。
3. **撤销的复制删的是"本窗口创建的那一份"**，如果人在撤销前已经改过那份副本，改动随
   副本一起消失——一步之内的撤销，这个窗口可接受；不做脏检查。严重度：低。
4. **14 的另外两个"中"原地未动**：大文件的同步冻结（要把 `pathOp` 推出 GUI 线程，先有
   "一次写可以取消"的语义）与拖拽悬停无高亮（主题层一条规则）。归属不变。
5. **标签/备注的删除仍无撤销**：确认两段式挡在前面（17d），归并可原路变回去（17d 的
   账），单文件标签删了可以重加——一个通用撤销栈服务这三个手动可逆动作仍不值。
   严重度：低。
