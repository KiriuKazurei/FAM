# 开一扇窗要 1.1 秒：首屏时间的主导项不在数据通路上

- 增量：5（顺带量到的，不是本次改出来的）
- 提交：`2200594` 的验证过程
- 涉及：`apps/fam-shell/src/main.cpp`、`src/mainwindow.cpp`（`--self-check` 日志）

## 1. 描述问题

v2 的目标是"点目录 → 50µs 返回、一屏之内画出来"。数据通路确实做到了
（`fam_open_dir` 239µs，300 条目录 28–35ms 后有行，见
[v2-wire-and-windowing.md](v2-wire-and-windowing.md)），但真机跑 `--self-check` 时，
从进程起来到"目录打开"之间始终隔着 **1.1 到 1.3 秒**，与目录大小无关。

这条时间不是本次引入的：v1 走的是同一段（`MainWindow` 构造 → `show()` → 才开始做事），
但它挡在"10ms 开目录"这个卖点前面，不写清楚就会被当成 v2 没做到。

## 2. 分析问题

把 `QElapsedTimer` 打在四个点上，同一条命令连跑三次（机器静置，Temp 下 300 条目的目录）：

| 观测点 | 第 1 次 | 第 2 次 | 第 3 次 |
| --- | --- | --- | --- |
| `QApplication` 起来（进程入口起算） | 56 ms | 61 ms | — |
| `fam_core_new` 返回（构造起算） | 8 ms | 9 ms | — |
| 控件建完（构造起算） | 77 ms | 96 ms | 89 ms / 90 ms |
| `window.show()` 返回（进程入口起算） | — | 1224 ms | 1180 ms / 1280 ms |
| 首屏行数到位（构造起算） | 1076 ms | 1198 ms | 1122 ms / 1227 ms |

**`show()` 自己吃掉约 1.09–1.19 秒**（"控件建完"到"show 返回"之差），三次都是这个量级，
所以不是一次性的冷启动，而是每次都要付。

顺带被排除的几项：

- **不是 Qt/进程启动**：`QApplication` 只花 56–61ms。若防病毒在扫那 50MB 的 `famcore.dll`
  或 Qt6 的 DLL，这笔钱会先出现在这一行。
- **不是核心**：`fam_core_new`（配置 + `TagStore::open` + 起 pipeline + 起 loader 线程）8–9ms。
  这本身是个好消息：核心侧的启动成本已经很小。
- **不是数据**：`show()` 发生在 `fam_open_dir` 之前，那一刻模型是空的（0 行），
  窗口里没有任何东西可画。所以 1.1s 与目录大小、行数、缓存冷热都无关——
  这一点由"同一命令换 2 条目与 300 条目目录，差值不变"支持。

**没有做下去的归因。** `QWidget::show()` 里面至少有：平台窗口创建、样式/调色板初始化、
DWM 第一次合成、以及第一次 `paintEvent`。要分开它们，最直接的做法是在同一个二进制里
`QWidget bare; bare.resize(...); bare.show();` 与完整窗口对比（前者只走平台窗口 + 合成，
后者还走我们的控件树与 style 计算）。本次没做，因为那需要一个只为诊断存在的开关，
而它属于增量 8（UI）的工作面。

**一个未排除的混淆项**：壳链接的是 **debug** 构建的 `famcore.dll`（46–50MB，未优化）。
`show()` 在 Qt 自己的 release DLL 里，理论上不受我们 DLL 优化级别影响，
但"换成 release DLL 后这 1.1s 是否还在"没有测过。

## 3. 解决方式

**没有解决。** 本次只做了两件事，让这条时间从"感觉慢"变成"可核对的数字"：

1. `--self-check` 除了写截图，还写 `<png>.log`（窗口化程序没有控制台，
   光有像素证明不了"这一行是被一次剪裁删掉的"还是"重绘时重新取到的"）；
2. 上面四个观测点的 `qInfo`，消息处理器在 `MainWindow` 构造**之前**装好，
   否则构造期的日志全部丢失（第一版就栽在这里）。

## 4. 解决方式效果评估

**正面证据。** 就是 §2 那张表：三次独立运行，`show()` 的开销 1091/1128/1190ms，
且核心侧 `fam_core_new` 8–9ms、首屏数据到位 28–35ms——**慢的地方被定位到不在数据通路上**。
这直接改变了后续优化的靶子：如果继续按"再压一次行读取"排优先级，方向就错了。

**代价。** 四行日志与一个日志文件句柄；`--self-check` 现在会在截图旁边多写一个 `.log`。

**残留风险与局限（没解决什么）。**

1. **1.1 秒没有被归因，也没有被修**。已知它不在 Qt 启动、不在核心启动、不在数据读取。
2. 门槛"打开目录 ≤ 50µs 返回、一屏之内可见"目前只在**核心侧**成立；
   从用户双击到看见，还差这 1.1 秒的窗口开销。
3. 测量样本是同一台机器、同一目录、Debug 版 DLL、`--self-check` 这条特定路径；
   真实交互里 `show()` 可能与首次显示别的花销重叠，未测。
4. 下一步（留给增量 8）：同一个二进制里对比"裸 `QWidget` show"与完整窗口，
   把平台窗口/合成与我们的控件树分开；若前者也 1.1s，就要往 DWM/显卡驱动/Qt 平台插件方向查，
   那已经不是本项目能修的东西，需要写进"环境已知限制"。
